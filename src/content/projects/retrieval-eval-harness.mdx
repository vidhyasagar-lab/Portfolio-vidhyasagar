## The constraint

The system was a support-knowledge assistant over roughly 40,000 internal documents. It worked
well in the demo and unpredictably in production, and nobody could say which of those two was
representative — because the only test was a person asking it a few questions and forming an
impression.

That is a specific kind of failure. Retrieval quality is not a property you can eyeball: the
answer that reads best is often the one the model invented most fluently. Two changes that both
"felt better" had, when I eventually measured them, moved recall in opposite directions.

The constraint I was designing against was therefore not accuracy. It was **decidability** — I
needed a way to say yes or no to a change before it reached users.

## What I built

A harness that runs the full pipeline against a fixed evaluation set and reports four metrics per
run: faithfulness, context recall, answer relevance, and a hallucination rate measured against
labelled ground truth. It runs in CI on every pull request that touches retrieval, and a
regression beyond a set tolerance fails the build.

The evaluation set is the part that took the longest and matters most. I built it from 300 real
support queries stratified across question types — factual lookup, multi-document synthesis,
questions with no correct answer in the corpus, and questions where the corpus contradicts itself.
That last two categories are where naive RAG systems fail worst and where most public benchmarks
have nothing to say.

> The interesting cases are not the ones where retrieval works. They are the ones where the right
> answer is "I don't know", and the model says something anyway.

## The decision I'd defend

**LLM-as-judge for grading, with a human-labelled calibration set underneath it.**

The alternatives I considered:

- **Pure string overlap (ROUGE/BLEU).** Cheap and fast, but it scores paraphrases as failures.
  For a system whose whole output is paraphrase, this measures the wrong thing.
- **Full human grading.** The most trustworthy signal and completely impractical at the cadence
  I needed — 300 queries per run, multiple runs per day.
- **LLM-as-judge alone.** Fast and scalable, but a judge model has its own biases, notably a
  preference for longer and more confident answers.

I took the third option and bounded its weakness: 60 of the 300 items are human-labelled, and
every CI run scores the judge against those labels first. If judge-to-human agreement drops below
0.85, the harness reports itself as untrustworthy rather than reporting a result. The measurement
system gets measured.

## How I know it works

The claim isn't "the numbers went up" — I chose the numbers, so that would be circular. The
evidence is that the harness caught things the demo didn't:

| Change | Felt like | Actually measured |
| --- | --- | --- |
| Chunk size 512 → 256 | Sharper answers | Recall 0.71 → 0.58 |
| Added reranker | Slower, no visible gain | Recall 0.58 → 0.89 |
| Larger generation model | Noticeably better prose | Faithfulness unchanged, cost +240% |

The third row is the one that changed how I work. The bigger model produced answers everyone
preferred in a blind read and was no more faithful to the retrieved context. We kept the smaller
model and spent the budget on retrieval instead.

## What I'd change

**The evaluation set is static and will rot.** Real query distributions drift, and a frozen set
slowly stops representing production. I'd sample new queries from live traffic on a schedule and
route the ambiguous ones to human labelling, so the set stays alive.

**Latency is measured but not gated.** Cost and p95 are reported per run, but only quality can
fail the build. Given how much of the real-world experience is latency, that asymmetry is wrong,
and I'd gate both.
