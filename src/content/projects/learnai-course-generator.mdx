I wanted to know how far automated course generation could go before it stopped being
useful. Not the demo version — *write me a course on binary search* does that in one prompt.
The version a learner could sit down with and actually trust.

Trust turned out to be the whole problem, and it showed up somewhere I wasn't looking.

## What it does

You give it a topic, or you upload a PDF. It researches, plans, and writes a full course:
modules with explanations and examples, a ten-question quiz, and a timed assessment that gets
graded when you submit it. You can ask for the same material as a podcast script, an interview,
a flashcard deck, or five other formats — same pipeline, different voice.

If you uploaded a document, everything it writes is grounded in that document, with page and
section citations.

That part took a week. The next part took considerably longer.

## The bug you can't see

Ask a model for ten multiple-choice questions and it gives you ten plausible questions, four
plausible options each, and one marked correct. The questions are good. The explanations are
good. And some of the answer keys are simply wrong.

This is worse than it sounds, for one specific reason: **there is nothing in the output that
tells you which ones.** A wrong answer key doesn't look like a bug. It looks exactly like a
right one. You find it when a learner answers correctly, gets told they're wrong, and stops
trusting everything else on the page — including the nine questions that were fine.

I could review ten questions by hand. I could not review ten questions for every course, for
every user, generated on demand. The whole point was that nobody has to.

## Why I couldn't just ask it to check

My first instinct was the obvious one: after generating a question, ask the model whether the
answer is right.

This does almost nothing, and it took me a while to understand why. Shown its own prior answer,
a model agrees with it. Not because it re-derived the same result — because the answer is
sitting right there in the context, and agreeing is the path of least resistance. You get a
confident *yes, that's correct* on questions that are wrong. The check produces output that
looks like verification and carries none of the information.

So the requirement wasn't "check the answer." It was: **get a second opinion that cannot see
the first one.**

## Hiding the answer

The fix is small and does the entire job. Each question goes to a separate call that solves it
from scratch — question and options only, answer key withheld:

```python
async def verify_answer(question: str, options: str) -> str:
    """Independently solve a quiz/assessment question step by step
    WITHOUT knowing the claimed answer. Evaluates each option to determine
    the correct one. Use this to cross-check generated answers."""
```

It returns a structured verdict — `ANALYSIS`, `CORRECT_INDEX`, `CONFIDENCE` — and the pipeline
compares that index against the one the writer claimed. When they disagree, the independent
answer wins:

```python
if verified_idx is not None and verified_idx != q["correct_index"]:
    logger.info("[Agent:QuizValidator] Corrected: '%s' %d→%d",
                q["question"][:50], q["correct_index"], verified_idx)
    q["correct_index"] = verified_idx
```

Two calls to the same model, differing only in what one of them is allowed to see, disagree
often enough to be worth the call. That's the finding. Everything else here is plumbing.

> Every correction is logged with the question and both indexes. A silent fix would have
> traded a bug I couldn't see for a bug I couldn't audit.

The limit is real and I left it visible: short-answer questions can't be cross-checked this
way, so they aren't. They're graded at submit time by a model comparing the learner's answer
against the expected one.

## The rest of the pipeline

Five agents in a LangGraph state machine, each owning one job:

```
START → Planner → Writers → Reviewer ─┬→ Quiz Validator ──→ END
                                      └→ Assessment Validator ─┘
```

The **Planner** is a ReAct loop with tools — it searches your document, or researches the topic,
and decides how many modules the course needs rather than being told. The **Writers** run every
module concurrently through `asyncio.gather`, since they don't depend on each other. The
**Reviewer** scores each module out of ten and rewrites anything under seven.

Every node catches its own exceptions and returns usable fallback content while recording the
failure. One module failing produces one weak module, not a dead course.

## Grounding it in your document

Retrieval is hybrid: FAISS for meaning, BM25 for exact keywords, merged with Reciprocal Rank
Fusion. Semantic search alone misses the specific term a learner typed; keyword search alone
misses the paraphrase. Fusing them costs one extra query and covers both.

The part I'd point at, though, is smaller. Before embedding, each chunk gets a one-line
LLM-written description of where it sits in the document — Anthropic's Contextual Retrieval,
which they report cuts retrieval failures by around 49%. The trap is that those synthetic lines
are now inside your chunks, and if you hand them to the writer, it starts describing the
document instead of teaching from it.

So the contextualized chunks are what gets **searched**, and the original chunks are what gets
**written from**. Same index, two different jobs, and keeping them apart is what makes the
technique safe to use.

## What I got wrong

**The reviewer fails in the wrong direction.** It parses a `SCORE: X` line out of the
evaluation response. If the model returns text without that line, the module is treated as a
ten and passes untouched. A parse failure currently reads as a perfect score — precisely
backwards. It should retry or rewrite.

**I built it as though one process was forever.** The document cache, the FAISS indexes, and
the rate limiter all live in memory, which quietly pins the app to a single worker. Run two and
uploads and login lockouts start landing on whichever one answers. That's a Redis-shaped hole
I should have left room for at the start rather than after.

**Contextual Retrieval is one LLM call per chunk**, before generation begins. A hundred-chunk
PDF is a hundred calls of latency and spend the user waits through. Worth it for quality;
should be batched, or done lazily for chunks that actually get retrieved.

**There are no tests.** So I can describe the mechanism honestly, but I can't quote a defect
rate — and quoting a number I hadn't measured would be the exact failure this whole project
exists to prevent.
